# Proposal Pre-Send Check — бизнес-логика

Рабочий документ разработки. Расшифровывает `presend-landing-spec.md` до уровня, на котором
можно писать код: состояния, правила, структуры данных, события. Язык интерфейса — **английский**,
язык документа — русский.

---

## 0. Что мы вообще строим

Статический лендинг, который проверяет спрос на Chrome-расширение. Расширения нет.
Лендинг существует ради двух конверсий:

| Метрика | Событие | Где происходит |
|---|---|---|
| Оставил email | `email_submit` | модалка, после успешного `POST /api/lead` |
| Дошёл до цены и кликнул | `price_cta_click` | экран цены внутри той же модалки |

Всё остальное — hero, демо, секции, футер — воронка к этим двум событиям.
Любое решение в коде проверяется вопросом: помогает ли это одной из двух метрик.

**Границы:**
- нет вызовов LLM — демо полностью на клиенте, результаты захардкожены;
- нет регистрации, паролей, кабинета;
- нет биллинга — кнопка на экране цены никуда не ведёт;
- единственный сетевой запрос — `POST /api/lead`.

## 1. Домен: что такое «проверка предложения»

### 1.1 Категории проблем

Три категории. Категория определяет иконку, цвет и текстовку в UI.

| `category` | Что ловим | Базовая severity |
|---|---|---|
| `placeholder` | Незамененные заготовки: `[Client Name]`, `[Your Rate]`, `Lorem ipsum`, `XX%`, чужое имя клиента | `critical` |
| `ai_cliche` | Фразы, выдающие ChatGPT: `I hope this message finds you well`, `In today's fast-paced world`, `Let's delve into`, `I'm excited to leverage my expertise` | `warning` |
| `tos_risk` | Нарушение правил биржи: попытка увести в личку или на прямую оплату — `email me directly at`, `we can settle outside the platform`, `add me on Telegram` | `critical` |

«Базовая» severity — то, что почти всегда выставляется для категории. Severity хранится в данных
у каждой проблемы отдельно, а не выводится из категории: это позволяет сделать мягкое замечание
в зелёном примере, не ломая правило светофора.

### 1.2 Severity

| `severity` | Влияние на светофор | Смысл |
|---|---|---|
| `critical` | делает светофор красным | блокирует отправку |
| `warning` | делает светофор жёлтым | стоит перечитать перед отправкой |
| `note` | **не влияет** | мягкое замечание, «можно и так» |

`note` — расширение относительно спеки. Оно нужно потому, что спека требует зелёный пример
«без проблем, но с одним мягким замечанием»: любой `warning` по правилу светофора сделал бы его
жёлтым. `note` разводит эти два случая.

### 1.3 Правило светофора

```
есть хотя бы одна issue с severity=critical  → red
иначе есть хотя бы одна severity=warning     → yellow
иначе (пусто или только note)                → green
```

Подпись под светофором и число в ней:

| Цвет | Подпись | Что считаем |
|---|---|---|
| red | `Don't send yet — N blocking issues` | N = количество `critical` |
| yellow | `Send with caution — N things to review` | N = количество `warning` + `note` |
| green | `Good to go` | числа нет |

Плюрализация обязательна: `1 blocking issue` / `2 blocking issues`, `1 thing to review` /
`3 things to review`.

Цвет из данных (`verdict` у примера) — это ожидание, а не источник истины. Светофор считается
из `issues` по правилу выше; `verdict` в данных используется только как самопроверка в
dev-режиме (`console.warn` при расхождении). Так пример нельзя рассинхронизировать правкой issues.

## 2. Демо: модель и состояния

Демо — главный блок страницы. Задача: за 15 секунд объяснить механику так, чтобы человек захотел
этим пользоваться.

### 2.1 Что видит пользователь

Имитация будущего расширения: слева текст предложения, справа панель результатов проверки.
Над окном — переключатель из трёх готовых примеров.

Пользователь **не вводит свой текст**. Это принципиально: поле ввода + заранее подготовленный
результат = продукт врёт пользователю. Примеры честно подписаны `Example proposal`.

### 2.2 Три примера

Каждый демонстрирует свой цвет — за один экран виден весь диапазон работы продукта.

| # | `id` | Ярлык | Вердикт | Что показывает |
|---|---|---|---|---|
| 1 | `rushed` | `Rushed proposal` | red | Незамененные плейсхолдеры + прямая утечка на биржу |
| 2 | `ai-drafted` | `AI-drafted proposal` | yellow | Клише из ИИ-генерации, размытые формулировки |
| 3 | `clean` | `Clean proposal` | green | Проблем нет, одно мягкое замечание |

По умолчанию открыт **пример 1**: красный самый наглядный.

### 2.3 Структура данных

Один пример — один объект в `assets/js/demo-data.js`:

```js
{
  id: "rushed",
  label: "Rushed proposal",
  verdict: "red",                    // ожидание, проверяется против issues
  text: "Hi [Client Name],\n\n...",  // чистый текст, без разметки
  issues: [
    {
      id: "i1",
      category: "placeholder",       // placeholder | ai_cliche | tos_risk
      severity: "critical",          // critical | warning | note
      match: "[Client Name]",        // точная подстрока из text
      occurrence: 1,                 // какое по счёту вхождение подсвечивать
      title: "Unreplaced placeholder",
      detail: "You're about to send a template with the client's name missing.",
      fix: "Replace with the actual name from the job post."
    }
  ]
}
```

Правила данных (инварианты, их проверяет `validateDemoData()`):

- `match` встречается в `text` минимум `occurrence` раз, поиск буквальный (не regexp);
- `id` уникален внутри примера;
- порядок `issues` = порядок появления в панели; удобно держать его совпадающим с порядком в тексте;
- диапазоны подсветки не должны пересекаться — при пересечении побеждает issue, идущая раньше
  в массиве, остальные подсвечиваются без разметки (логируется предупреждение).

### 2.4 Подсветка строится программно

Подсветка в тексте строится **из поля `match`**, теги в `text` вручную не вставляются. Иначе при
правке примеров разметка разъедется, а `match` перестанет соответствовать тексту.

Алгоритм:

1. Для каждой issue найти `occurrence`-е вхождение `match` в `text` → диапазон `[start, end)`.
2. Отбросить пересекающиеся диапазоны (побеждает более ранняя issue в массиве).
3. Отсортировать по `start`.
4. Собрать HTML: сегменты текста экранируются, диапазоны оборачиваются в
   `<mark class="hl hl--{category}" data-issue-id="{id}">`.

Экранирование обязательно: текст примеров содержит `[`, `%`, кавычки, адреса вида `a@b.com`.

### 2.5 Сценарий взаимодействия

| Шаг | Состояние | Что происходит |
|---|---|---|
| 1 | `idle` | Текст примера без подсветки. Панель пустая, в ней кнопка `Check before sending`. |
| 2 | `scanning` | Клик по кнопке: кнопка блокируется, по тексту сверху вниз идёт полоса сканирования ~1.2 с. Событие `demo_run`. |
| 3 | `done` | Светофор загорается нужным цветом. Проблемы появляются в панели списком по очереди с задержкой 150 мс. Одновременно подсвечиваются фрагменты в тексте. |
| 4 | `done` | Клик по проблеме: соответствующий фрагмент подсвечивается ярче (`is-active`), карточка разворачивается и показывает `detail` и `fix`. Событие `demo_issue_open`. |
| 5 | `idle` | Смена примера: состояние сбрасывается в исходное, прогон запускается заново. Событие `demo_example_switch`. |

Задержка 1.2 с нужна не для красоты: мгновенный результат читается как заранее записанный и
убивает доверие к демо.

Мелочи, которые ломают демо, если их не оговорить:

- повторный клик по кнопке в состоянии `scanning` игнорируется;
- смена примера во время `scanning` отменяет текущий прогон (таймеры сбрасываются), новый пример
  открывается в `idle`;
- в состоянии `done` кнопка меняется на `Run again` и перезапускает прогон;
- раскрыта может быть одна карточка одновременно; повторный клик по ней сворачивает её;
- `prefers-reduced-motion: reduce` → без полосы сканирования и без стаггера, результат появляется
  сразу после 1.2 с (задержка остаётся, она смысловая, а не декоративная).

### 2.6 Мобильная версия

Две колонки не помещаются. На узких экранах (`< 900px`) — текст сверху, результаты под ним; при
появлении результата страница автоматически скроллится к светофору.

## 3. Структура страницы

Порядок блоков сверху вниз:

1. **Hero** — заголовок про «зелёный свет перед отправкой», подзаголовок с болью (отправил с чужим
   именем в шапке → потерял заказ), кнопка `Get early access`.
2. **Демо** (раздел 2) — главный блок, должен попадать на первый экран хотя бы верхней частью.
3. **Три категории проверки** — что именно ловит, по одному короткому блоку на категорию.
4. **Как это работает** — три шага: ставишь расширение → пишешь предложение как обычно → жмёшь
   проверить перед отправкой.
5. **Для кого** — фрилансеры на Upwork, Fiverr, Contra и в прямых сделках.
6. **Финальный CTA** — повтор кнопки `Get early access`.
7. **Футер** — ссылки на privacy и terms.

Кнопки `Get early access` в hero и в футере открывают **одну и ту же** модалку сбора email.
Различаются только параметром аналитики (`hero` / `footer`).

## 4. Сбор email и экран цены

### 4.1 Модалка

Одно поле — email. Два состояния внутри одной модалки: форма → экран цены.

Валидация на клиенте:

1. непустое значение;
2. формат: одна `@`, домен с точкой, без пробелов;
3. блок одноразовых доменов по списку (`mailinator.com`, `tempmail`, `guerrillamail` и подобные) —
   домен приводится к нижнему регистру, сравнение — точное совпадение или вхождение ключевого
   слова (`tempmail`, `guerrillamail`), чтобы ловить зеркала вида `tempmail.plus`.

Ошибка показывается под полем, фокус остаётся в поле, запрос не отправляется.

Текст в модалке честный: расширение ещё не запущено, мы напишем, когда откроем доступ.
Никаких «скачать сейчас». Отдельной строкой рядом с кнопкой — обработка данных и ссылка на privacy.

Поведение окна: фокус переходит в поле при открытии, `Esc` и клик по подложке закрывают, фокус
заперт внутри модалки, при закрытии возвращается на кнопку-инициатор, `body` блокируется от скролла.

### 4.2 Отправка

```
POST /api/lead
{
  "email": "...",
  "product": "presend",
  "gclid": "...",        // из URL, если есть
  "utm_source": "...",
  "utm_medium": "...",
  "utm_campaign": "...",
  "utm_term": "...",
  "landing_path": "/",
  "ts": "2026-08-11T10:00:00Z"
}
```

Ответ `200 {ok: true}`.

| Исход | UI | Аналитика |
|---|---|---|
| `200 {ok:true}` | форма заменяется экраном цены | `email_submit`, затем `price_screen_view` |
| сетевая ошибка / не-200 | сообщение об ошибке, кнопка снова активна, можно повторить | **ничего не отправляем** |

Пока кнопка в полёте — она заблокирована и показывает `Sending…`; повторный submit игнорируется.

`gclid` и utm-метки читаются из `location.search` при загрузке страницы и складываются в
`sessionStorage` — иначе при переходах внутри страницы (privacy, terms и обратно) они потеряются.
Уже сохранённые значения не перезатираются пустыми.

### 4.3 Экран цены

Показывается **сразу после успешной отправки email**, вместо формы, в той же модалке.
Не отдельной страницей — переход на новую страницу теряет часть пользователей, а это вторая
целевая метрика.

Содержание: `$12/month`, приписка про early-bird (первые пользователи получают первые 3 месяца за
половину), кнопка `Lock in early-bird price`.

Кнопка ничего не делает, кроме события `price_cta_click` — после клика показывает
`Thanks — you're on the list. We'll email you before launch.` и деактивируется.

## 5. Аналитика

GA4 через gtag. Все события — с параметром `product: "presend"`.

**Целевые** (импортируются в Google Ads как конверсии — переименование потом будет больно):

| Событие | Когда | Параметры |
|---|---|---|
| `email_submit` | успешный ответ от `/api/lead` | `product` |
| `price_cta_click` | клик по кнопке на экране цены | `product` |

**Вспомогательные:**

| Событие | Когда | Параметры |
|---|---|---|
| `demo_run` | запуск проверки в демо | `example_id` |
| `demo_issue_open` | раскрытие карточки проблемы | `category` |
| `demo_example_switch` | переключение примера | `example_id` |
| `cta_click` | клик по `Get early access` | `location`: `hero` / `footer` |
| `price_screen_view` | показ экрана цены | — |
| `scroll_depth` | 25 / 50 / 75 / 100 % | `percent` |

`scroll_depth` — каждый порог отправляется один раз за загрузку страницы.

Все события идут через одну функцию `track(name, params)`. Она:

- добавляет `product: "presend"`;
- ничего не отправляет, если нет согласия на аналитические cookie (раздел 6);
- в dev-режиме пишет событие в консоль.

## 6. Согласие и юридическое

Аудитория включает UK — GA4 без согласия сам по себе проблема.

- **Cookie-баннер:** минимальный, две кнопки — `Accept` / `Essential only`. Решение хранится в
  `localStorage` (`presend_consent` = `granted` | `denied`). При отказе gtag **не инициализируется**
  вообще — не «инициализируется и молчит», а не грузится.
- До ответа на баннер события не отправляются и не буферизуются: то, что произошло до согласия,
  считается несуществующим.
- **`privacy.html` и `terms.html`** — без них Google Ads не пропустит модерацию. Не откладывать на
  день запуска.
- Title, description, favicon, OG-теги.
- **Скорость:** никаких внешних шрифтов с блокирующей загрузкой, картинки в webp. Лендинг грузится
  из Финляндии на US/UK — каждая лишняя секунда бьёт по CR, а CR в KPI.

```

assets/js/analytics.js  consent, gtag, track(), utm/gclid, scroll_depth
assets/js/demo-data.js  три примера + validateDemoData()
assets/js/demo.js       машина состояний демо, подсветка, светофор
assets/js/lead.js       модалка, валидация, POST /api/lead, экран цены
assets/js/app.js        сборка: cookie-баннер, CTA, инициализация
```

Перед запуском заполнить `assets/js/config.js`: `gaMeasurementId` и `apiEndpoint`.

Инструменты разработки, в продакшен-сборку не входят:

```
tools/dev-server.js     статика + мок POST /api/lead (иначе воронку локально не прогнать)
tools/check.js          CLI: прогон текста предложения, --json даёт объект для demo-data.js
tools/rules.js          правила детекции — набросок логики будущего расширения
examples/*.txt          тексты предложений для прогона
```

`tools/rules.js` не участвует в работе лендинга: в демо детекции нет, там захардкоженные
`issues` (раздел 0). Правила нужны, чтобы проверять формулировки на живом тексте и собирать
новые примеры с уже посчитанными `match` / `occurrence`.
